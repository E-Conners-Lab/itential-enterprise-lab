# 0040 — Golden Config, compliance plan and device groups from NetBox intent, detection only

- **Status:** accepted
- **Date:** 2026-09-07
- **Amends:** ADR 0036 (consequence "Golden Config is out of scope"), PID 1.8 (new S4d)
- **Related:** ADR 0039 (devices through InventoryBroker), ADR 0041 (IOS-XE hostname defect)

## Context

PID S4d wires every Platform application to the EVE-NG lab; element 1 is Configuration
Manager: device groups, Golden Configuration trees, a compliance plan on a schedule. The
devices reach Configuration Manager through the built-in Inventory Manager adapter
(ADR 0039) with `ostype` equal to the inventory's netmiko platform (`cisco_ios`,
`arista_eos`), while Golden Config trees take the platform's own device types
(`cisco-ios`, `arista-eos`) and select the configuration parser by that type. Measured
2026-09-07 with a scratch `arista-eos` tree on `br1-sw01` (`ostype arista_eos`): a live
compliance run returned 6 passes including a `{d/}` disallowed line, so the tree's
`deviceType` chooses the parser and the underscore names need no custom parser.

The owner's earlier compliance agent (memory `work-laptop-agent-fleet`) compared NetBox
intent (hostname, loopback, backbone addresses) with the running config per device.
Golden Config variables are tree-level, and compliance-plan variable overrides are per
plan node, so a per-device value (the hostname, the management address) needs its own
tree node. Itential deprecates auto-remediation in Platform 6.5 and removes it in 7
(`updateNodeConfig`, `convertChangesToConfig`); the itential-builder golden-config skill
forbids wiring any remediation task.

## Decision

- **Documents in the repo, objects through the API.** `itential/golden-config/cisco-ios.j2`
  and `arista-eos.j2` are the baselines (management VRF, AAA and the automation user,
  DNS/NTP, SSH/eAPI, disallowed lines); the per-device leaf text (hostname, management
  interface, primary address) is rendered from NetBox by `ansible/playbooks/platform.yml`
  (`tasks/golden-config.yml`), the same NetBox query `itential.yml` uses for the inventory.
  Re-runs update the node templates in place (`PUT /configuration_manager/node/config`),
  attach missing devices and never delete a tree that a plan references.
- **One tree per OS**, `deviceType` `cisco-ios` / `arista-eos`, hierarchy
  `base/<site>/<device>`: `base` holds the OS baseline, the site node carries the site
  device group, the device leaf holds the NetBox intent and the device. Every inventory
  node is attached at its leaf.
- **Device groups** `site-<slug>` (dc1, br1, br2, wan) and `role-<slug>` (wan-edge,
  isp-core, spine, leaf, access, branch-switch) from the tags `itential.yml` already puts on
  the inventory nodes (site, role, platform). Groups are updated to the NetBox membership on
  every run.
- **One compliance plan** `lab-baseline` with one node entry per device leaf (12), throttle 5.
  It is run nightly by an Operations Manager schedule trigger on the generated workflow
  `wf-compliance-run-v1` (ConfigurationManager `searchCompliancePlans` by anchored name, then
  `runCompliancePlan`; plan id and run published as job variables), because Operations Manager
  is the platform's only scheduler and the same mechanism backs the nightly backups (S4d.2).
  The workflow takes no input: on 6.5.2 a schedule trigger does not persist `formData`
  (measured 2026-09-07: PATCH echoes it, GET returns null), so the plan is found by name.
- **Detection only.** No remediation task is ever wired. A violation is corrected through
  `wf-config-push-v1` (device, config lines, a `ViewData` approval in Work Center,
  `sendConfig`, then `write memory` through `sendCommand`), generated by
  `itential/workflows/build.py`; the remediation agent (S4d.5) gets that workflow as its only
  write tool.
- **Verification** `verify/test-06b-platform.sh` S4d.1: plan clean on 12 devices; hostname
  changed on one device per vendor through `wf-config-push-v1`; next run flags exactly those
  two; restored the same way; clean again. Direct SSH (`verify/devcmd.py`) is the second source
  for every state.

## Consequences

- `itential.yml` re-imports every `wf-*` (new: `wf-compliance-run-v1`, `wf-config-push-v1`);
  `platform.yml` then resolves the workflow ids for the schedule trigger, and `flowai.yml`
  re-resolves the agents' tools. Order: itential, platform, flowai.
- Rejected: custom parsers named `cisco_ios`/`arista_eos` (unneeded, measured); a regex
  hostname (`hostname {/\S+/}`, would not detect drift from NetBox); auto-remediation
  (deprecated, unsafe); one tree with both vendors (parsers differ).
- Interface intent beyond the management interface stays out of the tree until NetBox
  carries the link descriptions the topology template writes (`to <peer>`); today NetBox has
  only the management interface description.
