# 0080 — The Platform describes its own workflows: Describe Workflow runs the guide's walker on the Gateway

- **Status:** proposed (2026-10-11); decisions 2 and 3 taken as proposed by the owner (#163 merged); probes P1-P4 measured on the dev tier 2026-10-11 (below), then production the same day (job bd8c46be, the same four answers; the card read in Work Center)
- **Date:** 2026-10-11
- **Amends:** nothing; adds to PID section 3 (a new criterion set, S16)
- **Related:** ADR 0067 (workflow names), ADR 0068 (executable services on the Gateway, a repository pinned by
  commit), ADR 0069 (Studio assets change only through `build.py`), ADR 0074 (an external read-only service with
  least privilege), ADR 0077 (the pages people see), PR #162 (the workflow guide)

## Context

PR #162 gave every workflow a guide: `docs/workflows/<name>.md`, generated by `itential/workflows/describe.py`
from the workflow's own document, because the document now carries its steps (each task's `description` is the
title of the step `build.py` names) and the renderer needs nothing else. The same question is asked on the
Platform itself: someone sees `Rotate AWS VPN Key` in the task bar, or is about to run it, and wants to know what
it does, from the thing in front of them rather than from a repository.

What was measured and read before deciding (2026-10-11):

- The stored document is the committed one. `GET /automation-studio/workflows?equals[name]=<name>` answers one
  item with `tasks`, `transitions`, `inputSchema`, `outputSchema` and the step titles in every task's `description`
  (production, GET only). `equalsField=name&equals=` and `name=` are ignored by this endpoint (36 items back).
- No Workflow Engine task reads a workflow document (the task reference library: `restCall` is the only HTTP call,
  and it would carry its credential in the document).
- No open-source adapter exists for the Platform itself (the GitLab group's 50 projects searched for `itential`
  and `iap`). Building one means Adapter Builder and a maintained package.
- An Integration Model cannot do it: its token is self-managed, and the Platform's `/login` token expires.
- `itential-mcp` v0.14.0 (the lab's MCP server, FlowMCP-capable) has no document tool: `get_workflows` returns
  Operations Manager endpoints, `describe_project` component metadata; `describe_job` does return a job with its
  tasks, which Describe Job will want.
- A Gateway 5 executable service holds a Vault-backed credential as an environment variable per run (ADR 0068) and
  the runner already reaches Vault with `VAULT_ADDR` and the lab CA.

## Decision

1. **One read-only Gateway service, `platform-describe`, on this repository.** Actions `workflow` (this ADR) and
   `job` (decision 6). The code is `itential/workflows/platform_describe.py` (the service: login, one read, the
   answer) and `itential/workflows/describe.py` (the walker the pages use): the code that runs on the Gateway is the
   code tested here, and the guide on the Platform says exactly what the page in the repository says.
2. **The repository the Gateway clones is this one.** It is public, so no deploy key; it is pinned by a full commit
   SHA in `versions.yaml` (`platform_describe.repository.reference`), ADR 0068's rule for code the Gateway runs. The
   pin lags by one merge: a PR that changes the describer merges first, and the PR after it moves the pin to that
   commit on `main`. A test holds the pin to a commit that is an ancestor of `main`. (Owner to confirm: the
   alternative is the cloud-devops-pipeline repository, which would vendor a copy of `describe.py` behind a
   byte-identical test; rejected here for one source.)
3. **The credential is `svc-copilot`**, the read-only service account that already exists on both tiers
   (ADR 0063, `itential/copilot/roles.yaml`: AutomationStudio `apiread`, WorkFlowEngine `apiread`, OperationsManager
   `viewer` and `apiread`, no write method). Its password is seeded into Vault at `platform/svc-copilot` (key `password`)
   from `.env` by the Vault config play, as the device account's is, and reaches the service as the Gateway alias
   `svc-copilot-password` -> `PLATFORM_PASSWORD`, resolved by the server per run; only the Gateway's reader may
   read `platform/*`. The Platform's address and the account name are not secrets: the runner's environment carries
   `PLATFORM_URL` and `PLATFORM_USER` the way it carries `VAULT_ADDR`; the lab CA is `VAULT_CACERT`'s file. (Owner to
   confirm: a dedicated `svc-describe` account with only the two `apiread` roles is the narrower choice, at the
   cost of one more account to keep.)
4. **Read-only by construction.** The script sends `POST /login` and `GET`; any other verb or host is refused in
   code before a socket opens (the same guard `verify/prod-snapshot.py` has). It reads one workflow by name, or one
   job by id (`/operations-manager/jobs/<id>`), and prints one JSON object: `ok`, the name, the counts, the guide as
   Markdown and as HTML. The password is never in argv, in the output or in a log line.
5. **The workflow `Describe Workflow`** (`versions.yaml` `describe_workflow`): the input gate (the name, 1-80 of
   `[A-Za-z0-9 -]`), the service, then `guide` (the Markdown) and `summary` (name, tasks, steps, where it waits)
   published, and one Work Center card (`InteractiveHTML`, one button, the flying theme of ADR 0077) showing the
   guide as HTML. A service that fails or finds no such workflow ends the job with the reason in `error` and opens
   no task: the workflow reads, like `Get AWS VPN Status`. It runs on demand; a form follows when wanted.
6. **`Describe Job`** (the next PR): the same service, action `job`: the job's tasks and their states laid over the
   steps, so the answer is which path this run took, where it stopped and what the job said, in the guide's words.
7. **The agents** (after): the service as a Gateway Service tool on an agent, so "what does X do" and "what did
   job Y do" are answered from Slack through NetClaw by a deterministic walker, the model only relaying.

## Consequences

- The Platform answers about itself with the words the repository uses, and the two cannot drift: both read the
  same document with the same code.
- A second Gateway repository, and a service that logs in to the Platform. Its blast radius is a read-only account
  and GET; the account's roles are the ones `tests/test_copilot_access.py` already holds.
- The pin lag (decision 2) means the describer on the Platform is one merge behind the repository until the next
  PR; the guide pages in `docs/workflows/` are never behind.
- `itential-mcp` gains nothing yet. A `describe_workflow` tool contributed upstream would let FlowMCP serve the
  agents and the workflows alike with no Gateway repository at all; it is the better long-term shape, and the
  follow-up once this works.

On production the same run (job `bd8c46beb95a416daffe2966`) gave the same four answers, and P4 was read in Work Center itself: the card renders inside the task with its own scroll, the Seen buttons under it. The captures are in the LinkedIn hub, folder 22.

Two things the Platform's copy shows that the repository page does not, both to live with for now: the stored
`outputSchema` carries the job's own variables (`_id`, `initiator`, the input echoed back) and widens the `*_note`
types to a union, so "What it publishes" is longer on the card than on the page. A later change can leave the
Platform's own variables out.

## Alternatives considered

- **An adapter for the Platform.** None exists; `request_token` authentication would fit, but a generated adapter
  is a package to maintain. Revisit if Itential publishes one.
- **An Integration Model.** Static tokens only; the Platform's login token expires.
- **`itential-mcp` through FlowMCP.** The right long-term shape (one server for agents and workflows), but v0.14.0
  has no document tool; the contribution is the follow-up, not the start.
- **`restCall` from the workflow.** The credential would sit in the document.
- **The pages embedded in a lookup workflow.** Reads nothing live; useless for Describe Job.
