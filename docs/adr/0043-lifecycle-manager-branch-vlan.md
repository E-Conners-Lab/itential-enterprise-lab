# 0043 — Lifecycle Manager model `branch-vlan`: actions by workflow name, delete through the governed push, instances from NetBox

- **Status:** accepted
- **Date:** 2026-09-08
- **Related:** ADR 0036 (`wf-branch-vlan-v1`), ADR 0040 (`wf-config-push-v1` is the only write path), ADR 0044 (the JSON form approval), PID S4d.3

## Context

PID S4d.3 puts the branch VLAN service under Lifecycle Manager: a resource model with create and delete
actions, instances for the VLANs that already exist, a create/instance/delete round trip behind the Work
Center approval, and a recorded history. Measured on 2026-09-08 with throwaway objects on 6.5.2 (memory
`itential-platform-lessons`):

- An action may name its workflow. The model stores the name and resolves it to the current workflow id
  when the actions are validated or run, so the delete + import that `itential.yml` does on every `wf-*`
  does not break the model (unlike Tool Registry references, ADR 0038). A model update is a PUT of the full
  document.
- `run-action` starts a wrapper job of type `resource:action` that runs the action workflow as a **child
  job** named after the workflow; the child receives the action inputs and, on update/delete, the current
  data as the job variable `instance`. The workflow's `instance` job variable at the end becomes the stored
  instance data. A create whose workflow ends in error still writes an instance (data null) that blocks the
  name; only an action retires an instance (there is no instance delete route).
- Instance import takes the bare document (`{name, description, instanceData}`) and validates it against
  the model schema. The builder skill is wrong on both the import wrapper and `includeDeleted`.
- EOS answers `show vlan <n>` for an absent VLAN with `% VLAN n not found in current VLAN database`, and
  Gateway 5 reports that command as successful with the text in `output`.

## Decision

- **Document** `itential/lcm/branch-vlan.yaml`: schema `branch` (br1|br2), `vid` (11-99), `vlan_name`,
  `switch`, `netbox_vlan_id`, `status` (reserved|active|deleted), all required, no extra properties;
  actions `Create` (`0c01`, type create, workflow `wf-branch-vlan-v1`) and `Delete` (`0d01`, type delete,
  workflow `wf-branch-vlan-delete-v1`), no pre/post transformations: the workflows publish `instance`
  themselves. `ansible/playbooks/tasks/lcm.yml` creates the model, replaces it in place when the document
  differs, and asserts every action `runnable` through the validate endpoint on every run.
- **Instances** are named `<branch>-<vlan_name>` (known before the run; the VID is chosen inside it). On
  every run the play imports one instance per NetBox VLAN in the branch groups `br1-user` and `br2-user`
  that has none (switch `<branch>-sw01`, status from NetBox). The play never retires an instance: that is
  the Delete action's job.
- **`wf-branch-vlan-v1`** keeps its inputs and publishes `instance` on both paths (applied and no-op), so
  the create action stores the same data whether the VLAN was new or already there. Its approval is the
  JSON form of ADR 0044.
- **`wf-branch-vlan-delete-v1`** (generated by `itential/workflows/build.py`): reads the instance data,
  runs `show vlan <vid>` on the switch through Gateway 5 and, only when the VLAN is present, starts
  `wf-config-push-v1` as a child job with `no vlan <vid>`, so the device write keeps the single governed
  path and its approval card (ADR 0040); the NetBox VLAN is deleted **after** the device, so a rejected
  push changes nothing. It publishes `changed`, `netbox_deleted`, `switch_changed` and the instance with
  status `deleted`. Run on a retired VLAN it is a no-op (`changed` false, no push job).
- **A rejected or failed action is finished by cancelling its execution.** Measured: a job in error is
  retryable on 6.5.2, so the wrapper's `childJob` task, and with it the execution, keep waiting after the
  action workflow ends in error (a rejected create after its rollback, a rejected push under the delete).
  `POST /lifecycle-manager/action-executions/<id>/cancel` is the terminal step: it cancels the wrapper and
  the child jobs, retires the instance of a create (nothing was created) and keeps the instance of a
  delete (nothing was deleted). The workflows keep their Phase 5 error semantics; the operator cancels in
  the Lifecycle Manager UI, the verify through the API.
- **Verification** `verify/test-06b-platform.sh` S4d.3, on br2 so it never collides with the br1 VLAN of
  test-05/test-06: model and form present with every action runnable; one instance per NetBox branch
  VLAN; create action -> child job pauses -> the pending Work Center item's resolved variables show branch,
  VID, name, switch and the NetBox VLAN id that NetBox confirms as reserved -> approved -> instance active,
  VLAN active in NetBox and present on br2-sw01 over direct SSH; the delete workflow with a rejected push
  card leaves NetBox and the switch untouched and waits until both jobs are cancelled; delete action -> the
  push card approved -> NetBox VLAN gone, `show vlan` says not found, instance gone from the list; the two
  executions with their job ids; the delete workflow on the retired VLAN completes with `changed` false and
  no push job; a second create rejected on the form rolls its reservation back, and cancelling its
  execution retires the instance.

## Consequences

- `itential.yml` imports the new workflow; `platform.yml` (element 3 after elements 1 and 2) runs after it;
  `flowai.yml` is unchanged. The LCM `runAction` workflow task can become an agent tool in S4d.5.
- Work Center: the card of a create belongs to the child job `wf-branch-vlan-v1`, the card of a delete to
  the grandchild `wf-config-push-v1`; the verify helpers find children through the jobs' `ancestors`.
- An execution that waits on an errored job is visible in Lifecycle Manager as running; job history keeps
  the errored child. Task ids must be 1-4 hex digits: one bad id (`1g`) failed the whole import batch, so
  `tests/test_lcm.py` checks every generated workflow.
- Rejected: LCM-generated action workflows (`/edit`, opaque documents); pre/post JSTs (one more object type
  for one field rename); instance groups (need `LCM_GROUPS_ENABLED`); a delete workflow with its own
  `sendConfig` (a second device write path); referencing workflows by uuid (breaks on every re-import).
