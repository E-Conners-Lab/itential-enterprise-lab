# 0038 — Structured CLI output: Genie for Cisco, TextFSM for Arista, on a Gateway 5 runner node

- **Status:** accepted
- **Date:** 2026-09-07
- **Amends:** ADR 0035 (dev-stack layout), PID 1.7 (S4c criterion 7)

## Context

The agents (ADR 0037) reason over device state. Gateway 5's native `send-command`
returns text; the owner wants structured JSON, with Cisco's Genie parsers for the
IOS-XE nodes and TextFSM (ntc-templates) for the Arista nodes (owner decision
2026-09-07). The owner's earlier lab took the same direction with a Gateway 5
python-script service calling Arista eAPI (`E-Conners-Lab/iag5-eapi-stats`).

Gateway 5 runs inline code (`runCode`) and python-script services in an isolated
virtual environment built per package list from PyPI, cached by that list. Measured
on 2026-09-07: the stock `automation-gateway5:5.5.2-amd64` image is Alpine 3.24
(musl) with Python 3.14.7; `pip install pyats` there fails with "no matching
distribution" because Cisco publishes manylinux (glibc) wheels for Python <= 3.13
only. TextFSM and ntc-templates are pure Python and install anywhere. `iagctl` is a
static Go binary.

Gateway 5 supports distributed execution: a server node keeps the Gateway Manager
connection and the gRPC API, runner nodes execute; they share a store, which must
be etcd v3.5 for a cluster (`GATEWAY_STORE_BACKEND=etcd`).

## Decision

- **Gateway 5 becomes a three-container cluster** on VM 205: `etcd` (quay.io
  `v3.5.21`, Docker network only, no TLS until Phase 9), the stock `gateway5` server
  with `GATEWAY_STORE_BACKEND=etcd` and `GATEWAY_SERVER_DISTRIBUTED_EXECUTION=true`,
  and `gateway5-runner`, built on the VM by `ansible/playbooks/itential.yml` from
  `itential/gateway5-runner/Dockerfile`: `python:3.12.14-slim-trixie` (digest
  pinned) plus the `iagctl` binary copied from the pinned gateway image. Every
  execution, native services included, runs on the runner; the runner's
  `/var/lib/gateway` (venv cache, pex, task workspaces) is a named volume.
- **Parsers as pinned pip packages**, not baked into the image:
  `pyats==26.8`, `genie==26.8` (Cisco), `textfsm==2.1.0`, `ntc-templates==9.2.0`
  (Arista) in `itential/versions.yaml` `parsers`. One package list for both vendors
  means one cached venv (~790 MB, first build ~70 s, then ~2 s per parse).
- **`wf-show-command-v1`** (generated by `itential/workflows/build.py`): device +
  command -> `send-command` -> NetBox platform slug of the node -> `runCode` with
  the parse script (slug substituted into the code; the platform maps
  `ios-xe`->Genie `iosxe`, `eos`->ntc `arista_eos`) -> job variables `raw`,
  `parsed`, `parser`, `parse_error`. Agents get this workflow as their show-command
  tool; `wf-show-version-v1` stays as the S4.3 raw-text check.
- The local sqlite `gateway.db` of the server is abandoned: it held only the
  built-in services and host keys, both re-created in etcd on first start.

## Consequences

- VM 205 gains ~300 MB RAM (runner idle) and ~1 GB disk; still inside the 24 GB
  (`docs/resource-budget.md` unchanged).
- `verify/test-06-flowai.sh` S4c.7 checks both vendors against direct SSH;
  `tests/test_parsers.py` holds the pins, the Dockerfile, the override, the
  workflow, the play, the manifest and the agents to each other.
- Tool Registry entries for workflows are keyed by the workflow `uuid`, which
  changes on every delete + import (`itential.yml` does that for all `wf-*`).
  An agent then fails with `resource-not-active` on its old
  `workflow:<uuid>` tool. Rule: run `flowai.yml` after any workflow import;
  it re-resolves the references and diffs the agents' tools.
- Rejected: a parser sidecar HTTP service (bolt-on, not governed by Gateway
  Manager); a second all-in-one glibc gateway cluster (two clusters for one
  lab); TextFSM for Cisco too (works, but the owner wants Genie's richer schemas).
- Later: the eAPI python-script service pattern from `iag5-eapi-stats` can be
  registered on this runner as a Gateway 5 repository service; etcd and runner TLS
  with the lab CA in Phase 9.
